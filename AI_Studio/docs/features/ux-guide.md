# In-app help: Help panel, Guide page, tour

What changed for the tester (GUIDE-UI). The written topics, words and "I want to…" list are in `web/src/features/guide/content/` (GUIDE-CONTENT); this note covers the screens that show them.

## For the tester

- **Help button on every page.** In the top bar of every page (the sidebar has one too, below Settings). It opens the **Help panel**.
- **The panel knows where you are.** It shows *What is this page*, *What you can do here* (3 to 6 items, each with a button that goes to the exact thing or opens a topic), *Words on this page* (collapsed), and *What next*. It re-reads the address, so it follows you from page to page, including section changes (Runs > Schedules) and the test workbench's four tabs (Steps, Text, Code, History). Its buttons are only ever links and topic views: it never starts a run and never changes data.
- **Search.** A box at the top searches every topic, word and older name ("how do I run tests every night"). It ignores case and plurals, matches the start of a longer word, forgives a typo or two in words of five letters or more, and counts a title or keyword hit above a hit in running text. Nothing found suggests the "I want to…" list.
- **Three layouts, one panel.** Wide screens (1200 px and up): docked at 380 px beside the page, the page narrows, nothing is covered, the page stays usable. 1024 to 1199 px: floats over the right edge, non-modal. Under 1024 px: a full-height sheet that is a real modal dialog (the page behind is switched off with `inert`, Tab stays inside, a tap outside or Escape closes it). Escape closes the docked panel when the keyboard is in it; focus returns to the button that opened it.
- **The Guide** (`#/guide`): **I want to…** as large plain buttons first, then every topic grouped, with a search box. `#/guide/<topic>` shows: What it is, Why you'd use it, numbered How steps (on-screen names in bold), Good to know, an **Open it in the app** button, Words in this topic, Related topics, and "More technical detail" (the repository document's path as plain text). `#/guide/words` is the alphabetical glossary with search (it also finds the older names). Breadcrumb "Guide". Printing hides the sidebar, top bar and panel.
- **Open it in the app.** Uses the project you are in (the address, the test's project, or the last project you had open). With none, one project is used as it is; several are offered in a list first; none says so and points at starting one. It is only a link.
- **The tour (round 22).** 63 steps in seven chapters, each a short card pinned to a real element: **Getting around** (sidebar: Projects, Security assessment, Settings, Help, your account; the project tabs one by one), **Making tests** (New test and each way: Describe it, Record it in a browser, Build steps by hand or Write it as text, Write code, Import tests; a test's Steps, Text, Code and History tabs; Save and Save and run; Reusable steps, Shared elements, Test data), **Running and results** (Run and its panel, the run strip and Stop run, All runs, one run, why a test failed with its evidence, Schedules, Trends and unreliable tests), **Release and Setup** (Releases, the sign-off decision, Manual checks, Compliance, Runners and Add a runner, Environments, Alerts, Issue tracker, Device farms, Storage and backup, Testing type), **Phones** (Mobile app, Explore with AI, the Explorer view), **Security assessment** (security home, Applications and authorization, New assessment, Assessments and their progress, Emergency stop, findings and their states, Reports and Download as Excel, Activity, Notifications) and **Help** (Help, the Guide, "?" buttons and tips, taking the tour again).
  - It starts at a **chapter list** (each chapter with its number of steps, "Start from the beginning", "Continue where you stopped" when there is a saved place, "Not now"). The card says "Step 7 of 49 · Running and results" and has **Back**, **Next** (**Finish** on the last), **Skip chapter** (not in the last chapter), **End tour**, and a **Chapters** list to jump. Right and Left arrows go on and back while the keyboard is in the card; Escape ends it. Each step puts the keyboard on Next; steps are announced politely.
  - **What is left out.** Steps whose need is missing are left out before it starts, so the counter is right from the first step: Phones only when the project has a phone app; Security assessment only when the module is on and the project includes it (the sidebar entry and Testing type only when the module is on); your account only when someone is signed in; a test, a failing test, a run or a release only when the project has one; a project for security assessment only leaves out the functional chapters. With no project the steps that need one become one plain card. A step whose element is not on the page (the sidebar on a phone, a control that went away) is passed over quietly and the counter drops it. Two steps point at a stand-in when what they explain only exists while something runs: the run strip (else Run) and the Explorer view (else the Overview tab).
  - **Only opens pages.** It uses the project you are in (else the first one), opens each step's page itself (Tests, a test's tabs, a failing test, Runs and its sections, the latest run, Library, Release, the latest release, Setup sections, the security pages, the Guide), and never clicks, opens a menu or dialog, or submits. It reads what it needs with GET requests only.
  - **Placement.** The element is scrolled to near the top of the window and outlined; the card sits below it, else above it, else at the bottom, never off screen (also at 375 px, where it uses the full width). The card follows the element when the page moves it while loading. The page is not dimmed.
  - **Remembers.** Ending early keeps the step in `localStorage` key `guide.tour.at`; the chapter list then offers to continue there. Finishing forgets it.
  - **Starting it.** Help panel, **Take the tour** (opens the chapter list); the Guide page, **Take the tour** and a **The guided tour** section with one button per chapter (a chapter that does not apply to the project opens the chapter list with a line saying so).
- **First visit.** A small card, "New here? Take the guided tour, one chapter at a time." with **Start the tour** and **Not now**, bottom corner, never blocking. The choice is kept in `localStorage` key `guide.tour`. With storage blocked it asks again on each load but never twice in one visit.
- **"See how" lines.** On the empty Tests page, empty Runs, empty Library sections (Reusable steps, Shared elements, Helpers, Test data, Test accounts) and the welcome page: "Not sure how this works? See how" opens the matching topic in the panel.

## How it is built

- `web/src/features/guide/`: `places.ts` (the help text for 38 places and `placeOf`, which turns an address into a place), `search.ts`, `where.ts` (`WhereTo` to an address, with the router's own builders), `tour-steps.ts` (pure data and rules), `HelpContext.tsx` (open state, view, the place a page may refine with `useHelpPlace`), `HelpPanel.tsx`, `TopicView.tsx`, `GuidePage.tsx`, `Tour.tsx`, `SeeHow.tsx`, `current-project.tsx`, `guide.css`.
- Small hooks into shared files: `Shell.tsx` (buttons, panel, room for it), `main.tsx` (providers, `#/guide`), `lib/router.ts` (`routes.guide`, `guideTopic`, `guideWords`), `ui.tsx` (`EmptyState seeHow`, `Menu dataTour`), `data-tour` marks (round 22: sidebar items, every project tab, every section tab of Runs, Library, Release and Setup (`<place>-<section>`, set in `ProjectHub`), the security tabs (`sec-<tab>`), the workbench tabs (`wb-<tab>`) and editor, New test, Run, the run strip, a run's tests, a test's Last run, the sign-off, the runners card, the Mobile app setting, Explore with AI, the Explorer view switch, Testing type, the security projects list, Emergency stop, the report downloads, the Guide's "I want to" list and Take the tour, Help; `tests/guide-unit.test.ts` fails when a step points at a mark that does not exist or a mark is not used), `NewProject.tsx` and `ProjectOverview.tsx` (the welcome and plan places), and `SeeHow` lines in six empty states.
- A page that is more specific than its address says so with `<HelpPlace place="…"/>` (the first-run welcome page and the plan).

## Decisions and limits

- **The first-visit offer is not shown to automated browsers** (`navigator.webdriver`), unless the address has `?tour=1`; `?notour=1` is always quiet. That keeps every existing UI test unchanged (none had to be edited). A real person never has the property.
- The Help button sits in the top bar, which every page has, instead of inside each page's own header; the sidebar has the second one.
- "What next" is static text. It does not look at real project state (a cheap version would need a request on every page).
- The place help names topics by id; a topic that is missing from the content falls back to a search (a test fails when one is missing, so it cannot go unnoticed).
- A person who starts the tour on a page of a project that has no tests, runs or releases does not see the steps that open one (the counter says so).
- Some pages the tour opens ask the server with a POST that only reads or converts (the Code tab's script preview, the Text tab, a ticket for the live event stream), as they do for anyone who opens them. `tests/tour-ui.test.ts` walks every step of a project that has everything and checks that each such request is one the read-only viewer role may make, and that no dialog opened.
- A few steps describe controls rather than open them (New test's entries, the Run panel, the Save bar that only shows after a change, the Explorer view and the run strip that only show while something runs). Opening a menu would mean clicking for the person, which the tour never does.
- The tour's own text is not translated. Real Safari and real phones were not tried; the tour was checked in Playwright's Chromium (desktop, 390 px and 375 px).
- Not covered: the Guide and panel have no translations; the topic text is only as good as the content; screenshots are written only when `GUIDE_SHOTS` is set.
- Fixed on the way: with browser storage blocked, the whole app failed to start (the access key was read from `localStorage` without a guard). `web/src/api.ts` now keeps the key in memory in that case.
