# Test recorder and inspector

Click through your application in a real browser, watch the steps appear, pick elements to check, and save the result as a normal web test that the platform then runs for real. Nobody has to write a locator.

## What a user sees

- **Record a test** on a project: enter the address (or, with an environment chosen, a path on that environment's site), choose whether to show the browser, and start. A Chromium window opens on the computer that runs the platform. Every click, typed value, choice, tick and Enter that changed something appears as a step in plain words ("Click the button "Add to cart"", "Type the password into the field labelled "Password"").
- The page warns before recording: "Don't type real personal data or secrets while recording." Ordinary values are recorded as typed because they become the test's data.
- **Inspect**: turning it on shows a hover outline and the best locator in the recorded browser. A click does not act on the page. In *locator* mode it only picks the element and shows its candidate locators, each with how many elements it finds ("1" is unique). In *assertion* mode the click also adds a check: is visible, is not visible, shows this text, holds this value, is enabled or disabled, or the number of items in a list.
- **Edit**: every step lists alternatives (best first, with match counts). Choose another locator, edit a typed value or a check's expected text, delete a step, or turn a step's locator into a **shared element** of the object repository.
- **Stop** closes the browser and keeps the steps. **Discard** closes it and forgets everything. The session also ends after 20 minutes without activity, after 60 minutes in total, or when the person closes the recorded window.
- **Save** asks for a title, builds a canonical web spec (origin `recorded`), stores it as a normal test and queues a normal validation run. The recording is judged by that real run: if it does not replay, the test is kept as a normal test that is not validated (needs review), never marked passing.

## How it works

- **Session**: `src/platform/recorder-service.ts` launches the platform's own Playwright Chromium in a fresh context (no cookies, storage, extensions or granted permissions) and installs `src/engine/recorder/page-script.ts` in every page. One session per project (a second start is `409`); sessions of different projects are independent. State is in memory: a platform restart ends it, and a well-formed unknown id answers a `failed` recording with a plain message.
- **Page to platform**: the injected script reports through a Playwright binding whose name is random per session. It keeps a private reference and deletes the global at once, so the page cannot call, replace or read it, and every message carries a session token. The control that switches inspect mode is a randomly named, non-enumerable property. Events from anything but the first window's top page are ignored.
- **Capturing**: clicks resolve to the nearest meaningful ancestor (link, button, summary, role-bearing element, or a block with a pointer cursor). Typing is reported once per field with the final value (on blur, change, Enter, click elsewhere or leaving the page); two fills of one field become one step. A click on a text field, checkbox, radio, select or label is not recorded as a click (its fill, tick or choice is). Enter, Escape and Tab are recorded only when something changed within about a quarter of a second (a form submit, a DOM change, leaving the page). Only real (trusted) clicks and keys count; typed values and select/tick changes are accepted from Playwright's own synthetic events too, which is what lets tests drive the browser.
- **Navigation**: the first page is a `goto`. A page that starts within 2.5 seconds of something the person did is taken as the result of that action and is not recorded. Any other new page (a typed address, a script redirect after a delay) is recorded as a `goto`. A reload of the same address is not.
- **Locators**: the page derives candidates in this order: test id (`data-testid`), role plus accessible name, label, placeholder, text, then css (an id, a `name`, and finally a position path such as `li:nth-of-type(2) > button`). It counts what each finds; then Playwright's own locators confirm the counts and that the recorded element is really among the matches (the element carries a temporary `data-aitp-pick` attribute for about 2.5 seconds for that check). The first unique candidate wins, up to four others are kept as alternatives. Text longer than 60 characters, and anything that looks generated (long hex or uuid, three or more digits in a row, dates and times, counters such as "3 items", random suffixes) is never used as a locator unless nothing else identifies the element, and the step says so. A position-based locator says so as well.
- **Secrets**: a password field, an `autocomplete` of `one-time-code`, `cc-number`, `cc-csc`, `current-password` or `new-password`, or a field whose name, id, label or placeholder says password, one-time code, card number or security code, is **never read**. The page sends only "a secret was typed here"; the step is a fill with `{{credentials.password}}` (`{{credentials.totp}}` for one-time codes, `{{secret.card_number}}` and `{{secret.card_cvc}}` for cards), `secret: true`, and the words "Type the password". The value of a secret step cannot be edited, and an assertion on a secret field's value is refused. A test sends every raw page message to a recorder tap and proves a typed password appears in none of them, in no API answer, spec, script, database file or artifact. Cookies and storage are never read. A username typed into an ordinary field stays as typed (it is not guessed).
- **Address guard**: the start address goes through the platform's guard. Pages are fetched one hop at a time through the platform, and each redirect target is checked **before** the browser connects to it; a refused address stops the session (`stopped`, with a plain `error`, steps kept). Production environments need the same confirmation as running there (`confirmProduction`). Environment credentials are not used by the recorder.
- **Caps**: 300 steps (a note says when it is reached), values at 500 characters, assertion text at 120, descriptions at 240.
- **Browser cleanup**: the browser process id is read from the browser itself and kept. Stop, discard, timeout, a closed window, a crash, a refused address and platform shutdown (Fastify's close hook) all end in a verified closed browser; if it does not exit in time, that exact pid is killed. A last-resort `exit` hook kills any browser still believed alive. Nothing is closed by name and no other process is touched. The status becomes `stopped` only after the browser process is gone.
- **Save**: `routes/recorder.ts` builds the spec with `src/engine/recorder/spec.ts` and stores it through the normal spec-import route, so every import rule applies (address guard, shared elements, switched-off frameworks, data sets) and the test gets a script and a validation job like any imported test. When the project already has an application on the same site, it is used (so its saved sign-in details fill the password stand-in). For another site a new application is created and the answer says the project still needs sign-in details. When another job is running, the test is saved with `jobId: null` and a note.
- **Healing**: tests with origin `recorded` are healable like other journey tests (`HEALABLE_ORIGINS`).

## API

All routes need the API key when the server has one. The contract with the web UI is `.scratch/briefs/RECORDER-API-SHAPES.md` (with the additions listed at its end).

| Route | What it does |
| --- | --- |
| `POST /api/projects/:id/recordings` | `{ url, headed?, environment?, confirmProduction? }` starts a session (`201`, status `starting`). `409` one is active; `422` no browser installed, or `headed` without a screen; `400` a bad or refused address. |
| `GET /api/recordings/:rid` | The recording (poll every second while `starting` or `recording`). |
| `POST /api/recordings/:rid/inspect` | `{ on, mode?, check? }`. |
| `PATCH` / `DELETE /api/recordings/:rid/steps/:index` | Choose a locator, edit a value or check; delete (indexes close up). |
| `POST /api/recordings/:rid/steps/:index/share` | `{ name }` creates (or reuses, when identical) an element of the object repository and makes the step use it; `409` when the name belongs to a different locator. |
| `POST /api/recordings/:rid/stop`, `DELETE /api/recordings/:rid` | Stop (keep steps), discard. |
| `POST /api/recordings/:rid/save` | `{ title, category? }` answers `201 { testId, testKey, jobId, note? }`. |

## Recording on a runner agent

A runner agent (see `runner-agent.md`) can host the recording: the browser opens on the tester's own computer, where the application is reachable and where the person can see the window. The same page drives it; nothing about saving, sharing an element or validating changes.

**How it works.** The platform queues a *record task* for one agent. The agent runs the same recorder core as the platform (`src/engine/recorder/session.ts`) in its own process (so a crash or hang cannot take the agent down, and the browser dies with the task) and pushes the whole recording state to `POST /api/agent/tasks/:id/recording` about once a second (a quarter of a second when something just changed, never more than 5 per second). The page's `GET /api/recordings/:rid` shows what the platform last received. Edits from the page (`inspect`, `PATCH`/`DELETE` step, `stop`) are **queued as commands** and go out in the agent's heartbeat reply (the agent beats every second while recording; the protocol's interval is only a maximum); the agent applies a command, then pushes the new state naming the command in `acked`. The answer to such a request is the state as the platform knows it plus `pendingCommands: n`: nothing is shown as done before the agent confirms, so the page keeps polling (and should not offer a second edit while `pendingCommands` is above 0, because a step number refers to the list the agent has). When the agent finishes it posts a normal result, `ok: true` with no runs.

**Choosing where.** `POST /api/projects/:id/recordings` accepts `on: "platform" | "agent"` and `agentId`. Without `on`, a project whose runner setting is an agent records on the agent, and any other project records on the platform as before. The answer has `runner: { kind: "platform" }` or `{ kind: "agent", agentId, name }`. The platform refuses, with a plain sentence: no agent online (`409`), an agent that is offline (`409`), an agent that does not belong to the project (`404`), an agent that cannot record (no Chromium, or an agent program from before this feature, `422`), and a window requested from an agent with no display (`422`: "Maya's laptop has no display, so it can't show the browser window. Turn off “Show the browser window”, or use another agent."). One recording per project holds for both places (`409` with `details.recordingId`). The start address is reached from the agent's network: the platform only checks that it is http or https with no credentials in it, and fetches nothing for it, so private and loopback addresses are fine (the same rule as agent runs).

**The record task.** It goes through the normal task queue with `kind: "record"` and `record: { recordingId, startUrl, headed, idleMinutes, totalMinutes, maxSteps }`. It has no job: `job_id` is `rec-<recordingId>` and `adapter_id` is `record:<agentId>`, which is how only the chosen agent is offered it. Nothing that lists or cancels jobs matches it. It carries no credentials and is encrypted at rest like any task. A record task is never re-offered to another computer: when its lease runs out it fails.

**Lifecycle and loss.** Stop and discard are commands too. Saving a recording that is still running sends the stop, waits (a few seconds) for the agent's confirmation, then builds the test from the platform's copy of the steps. Once the agent has finished, edits to the steps apply to the platform's copy directly (there is nothing left to apply them), so a stopped recording can still be tidied before it is saved. No push or heartbeat for 45 seconds ends the recording as `stopped` with the error "Lost contact with <agent name>. The steps recorded so far are kept." (the steps can still be saved, and the task is told to give up if the agent returns). A task nobody claims within a minute fails with a plain message. A platform restart loses the session (as for local recordings); the agent notices (its heartbeat is refused), closes its browser and stops. Discarding drops the session at once, even when the agent says nothing. Validation after saving runs wherever the project's runner setting says, through the normal job path.

**What the platform does with what the agent pushes (it is semi-trusted).** Every push is validated against the protocol schema (at most 1000 steps, string lengths, 1 MB, 5 per second per task); a push for a task that is not a record task, not claimed by that agent, or already finished is refused. A step marked as a secret always carries the standard placeholder (the value sent is replaced and the description is rebuilt from the placeholder). The project's known credentials (application password and one-time secret, tokens, named roles) are scrubbed from every text of a push. Steps that open anything but an http(s) page are dropped, long text is capped, step numbers are renumbered. Step values are never logged. The agent itself never reads a password, one-time code or card field in the page (the same private binding as the platform's own recorder), records no cookies or storage, opens only http(s) addresses without credentials, and applies the step and time caps; it does not apply the platform's address guard (its own network is the point).

**What the agent needs.** Chromium installed for Playwright (the same discovery as for runs) to report `record: true`; a display to report `recordHeaded: true` (Windows: a signed-in interactive session, not a service; macOS: always; Linux: `DISPLAY` or `WAYLAND_DISPLAY`). A recording takes one of the agent's task slots for as long as it lasts.

**Limits of recording on an agent.** The page sees the agent's state about a second late. A step number in a queued edit refers to the agent's list, so apply one edit at a time. The headed window on macOS and Linux desktops and on a real second computer have not been exercised by the tests (they use headless Chromium on this machine). The shared elements chosen with `share` are kept by the platform (a step keeps its name while the agent's later pushes arrive), and are lost for a step the agent merges into a later one.

## Limits (honest list)

- **Frames**: actions inside any iframe (same-origin or not) are not recorded: the test spec has no way to say "inside this frame". Open shadow DOM works; its locators are position-based or css.
- **Drag and drop, file uploads, canvas, hover menus, right-clicks and touch gestures** are not recorded (a double-click is recorded as two clicks). Drag and drop and uploads add a note; add those steps by hand or use another way to reach the state.
- **Popups and new tabs**: the click that opens one is recorded, the new window is not, and a note says so. Only the first window is recorded.
- **Dialogs** (alert, confirm, prompt) are dismissed by the browser's default and not recorded. Multi-selects and range sliders are not recorded.
- **Navigation credit**: a typed address within 2.5 seconds of the last click or key is taken as that click's result and not recorded. A page that takes longer than that to start after a click is recorded as an extra `goto`; delete it.
- **Where it runs**: by default the browser opens on the machine that hosts the platform, so recording from a remote platform means a window on the server, not on your computer, and only works where someone can see that screen (headed off works anywhere but nobody can click in it). To record on your own computer, record on a runner agent (previous section).
- **Assertions** on text that looks generated are allowed (it is your explicit choice) but may not survive the next release. A recorded click on a locator that matches several elements fails strictly on replay (the alternatives show how many); choose a unique one.
- A recording is a starting point: apps with timing, animation or data that changes need checks edited by hand. The validation run says whether the steps replay; it cannot say whether the checks are the right ones.
- Sessions live in memory: a platform restart loses an unsaved recording.

## Tests

Recording on an agent: `tests/record-agent-unit.test.ts` (fast tier: protocol messages and their sync with the recorder's step, the exact-match route with path tricks, the push rules, the command queue, lost contact with an injected clock, where a recording runs, the agent's wire mapping, and the shared core driven through a fake page), `tests/record-agent.test.ts` (a real platform and a fake agent: refusals, the task, who may push, validation and secrets, commands and their acknowledgement, lost contact, an agent that never answers, discard, stop then save) and `tests/record-agent-e2e.test.ts` (the real agent program with its own headless Chromium against the real platform, the test playing the person: steps, a password that never leaves the page, inspect and pick, edits, stop with the browser process verified ended, save and a validation run that ends VALIDATED on the agent).

`tests/recorder-unit.test.ts` (browser-free, in the fast tier): ranking and alternatives, dynamic-value rejection, normalisation and caps, redaction table and wording, descriptions, golden spec, origin wiring, the injected script's shape (valid JavaScript, no forbidden literals, a secret's value is read on no code path). `tests/recorder.test.ts` (real headless Chromium launched by the platform and driven by the test as the person, a fixture app on port 5990, the real worker validating saved recordings): API-key protection, bad input, headed without a screen, environments and production confirmation, a long login-and-shop journey (typed values, password never leaves the page, click-caused navigation without a goto, typed address as a goto, test id over shared role name, text-only elements, position locators, popups and uploads noted), inspect in both modes without acting on the page, edits, sharing an element, stop with the browser pid verified ended, save, and a real validation run that ends VALIDATED with the sentinel password absent from API answers, raw page messages, the database, scripts and artifacts; one-time-code and card redaction; a recording that does not replay is not validated; discard; a closed window; idle and total timeouts; a refused start address and a refused redirect; the step cap; platform shutdown.
