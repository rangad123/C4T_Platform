# Run control and an honest Stop

What changed for the tester: one **Run** control, a live strip while a run goes, a Stop that says what it keeps, and a page for each run.

## What the tester gets

- **Run panel** (Tests header, test page as the arrow beside *Run again*, Runs page). *What*: failing now, this group, selected tests, all tests, not run yet, each counted; disabled when empty. *Against*: the project address or an environment, shown only when the project has environments; production keeps its confirmation. Where it runs (the person's own runner, or this server on a platform that runs tests itself) is named once, in the closing sentence; a busy runner adds that the run waits. *How*: other browsers and screen sizes, and "run failing tests once more straight away" (the platform's `retryFailures`). One sentence is computed from the choices (left out while the run cannot start: then one callout says why, with the way to Settings); no time estimate (the platform has no real total to base one on). A person who may look at the project but not run its tests (no `ai_studio.tests.run` in the project's `access`) sees *Run* switched off with the reason on hover and focus; the server refuses the run too.
- **No runner to choose** (round 45): every run goes to the runner of the person who starts it, so the panel offers no choice and the run start sends no `runnerId` ([runner-settings.md](runner-settings.md)).
- **Select scripts** in the Test scripts list adds a checkbox per row and a bar that counts; *Run selected* opens the panel with those tests.
- **Code scripts on your own computer**: in runners mode, when the run includes code scripts, a note before Start says "This run includes code scripts. They run on your computer with your user's rights." with a link to Your runner in Settings, where code scripts can be switched off. With them off, the panel's one callout says so and Start stays off. The list of tests does not say who wrote a script, so the note names nobody (`codeScriptsSentence` names the authors when given them). A run of a fixed list ("Run failing tests again") does not know which tests are code scripts, so it shows no note.
- **Run strip** (project pages, test page): "Running 7 tests, 3 done, 1 failing, On this server", elapsed time, the newest live event, a list of tests with state (waiting, running, passing, failing, needs a look, not run) and links, and **Stop run**. When the run ends it says how it ended until dismissed. On a test's page it shows only that test.
- **Stop** asks "Stop this run?" and says how many results are recorded now; "Tests that did not finish keep their previous result" is the platform's rule since UXP. A run reads **Stopped: 3 of 7 ran** on the Runs page, Overview and run page. Wording: *Stop run* for runs, *Stop exploring* for the AI exploration, *Stop building* for a test built from a description.
- **Run page** (`#/projects/:id/runs/:jobId`): what ran, where, when, how long, who started it (person, schedule, deploy, run sequence), every test with failures first and the reason line, "Changed since the last run" (newly failing / newly passing), and *Run failing tests again* / *Run these tests again* (the same environment for an environment run). An exploration lists the tests it created.

## Runs only on runners (`EXECUTION_MODE=runners`)

On the hosted platform every run goes to a runner. The website reads `executionMode` from `GET /api/config` and the person's own runner from `GET /api/me/runner` (`web/src/features/runs/runs-here.ts`, `web/src/features/runners/my-runner.ts`). Every start control asks the same hook, `useReadiness(needs)` in `my-runner.ts`, and shows a not-ready reason with the same callout (`RunnerNotReady`):

- "This server" is not offered anywhere: not in the Run panel, not for a phone exploration.
- Run, *Run again* and *Run suite* wait until the person's runner is set up, connected and able to run the tests (a busy one takes the run: it waits). Otherwise they say "Set up your runner in Settings to run tests." or "Your runner is offline. Start it on your computer, then try again." with a link to Your runner in Settings (`#/settings#runner`), or the server's own sentence from `can` on `GET /api/me/runner` (for example that it cannot run phone tests). The line under the Tests header, and the badge on a run, appear only when something is off: the runner is not set up or offline, or a run happened on a runner other than the person's own.
- A refusal from the server (409 with `details.code` `RUNNER_NOT_SET_UP`, `RUNNER_OFFLINE` or `RUNNER_CANNOT_RUN`) is shown with its sentence and a link to Settings.
- The Schedules panel says whether schedules really start: only while scheduling is on and runs can start (in runners mode, while the platform's dispatch is running). "Run now" is disabled while runs cannot start. Each schedule says whose runner its runs go to ("Runs on Priya's runner", the creator's name); a new schedule does not offer "Explore again" (the platform refuses it there), and an older exploring schedule says it does not run in this mode.
- Exploring (the application or a phone app) and "Describe it" say before the click, in the platform's own words, that they are not available in this mode yet, and cannot be started; the platform refuses them there.
- When a run with code scripts is going to the person's own computer, the panel says so before Start: "This run includes code scripts written by … They run on your computer with your user's rights.", with a link to Your runner in Settings, where code scripts can be switched off. Names come from a script's saved versions, so they are given for a single test's run; a run of several tests says "This run includes code scripts." without names.

## Platform additions (small, additive)

- `POST /api/projects/:id/runs` `{testIds?, retryFailures?, variants?}` starts the same validation job a schedule or test run starts, for exactly those tests (default: every test). 400 for an unknown test or variant, 422 when nothing can run, 409 while another run is active.
- `GET /api/projects/:id/runs/:jobId` reads one run test by test (`src/platform/run-view.ts`): `counts {planned, ran, passed, failed, findings, running, waiting, notRun}`, `tests[]` with `state`, `reason`, `durationMs`, `startedBy`, and `changes`. Everything is read from rows the run already wrote; nothing new is stored.

## Limits (honest)

- On this server, scripts run together and results are recorded when they finish, so during a run most tests show "running", not a live step. On a runner that sends live events (protocol 2), the strip and the run page show the test and step it is on as it happens; see [run-live-view.md](run-live-view.md). A protocol-1 runner sends progress lines only ("Finished 3 of 12 tests").
- "Changed since the last run" compares each test with its own previous result, only for runs of existing tests on the project's address (not environment, browser-check or exploration runs).
- Environment runs leave out phone and desktop tests (said in the panel's sentence).
- A run asked for by id lists is limited to 2000 tests.
- Before the click the panel knows whether the person's runner is set up, online, takes code scripts and can run the kinds of test chosen (from `can`; an older server without it leaves that to the click). Whether a test reaches a private address is checked by the platform when the run starts, and its refusal is shown in the panel. A run of a fixed list ("Run failing tests again") knows only ids, so the platform checks it.
- The page keeps one answer about the person's runner (`useMyRunner`): one request however many controls show it, read again every 15 seconds while one is on screen in runners mode, when the window gets the focus, when the panel opens and after the server refuses a start; a runner that goes offline between the read and the click is refused by the platform with a sentence, and the controls then say the same.
