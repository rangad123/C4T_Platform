# Site memory: start from what we already know

Re-analysing a site should not start from zero. After every analysis the platform keeps a small set of **structural notes** about the
application — its pages, journeys, sign-in page and API endpoints. The next analysis starts from those notes: the model is told what was
known, so it keeps journey and test names steady and spends its attention on what is new. The platform also works out, with plain
comparison and no AI involved, **what changed since the last analysis**.

The idea of a per-site knowledge base that later runs build on comes from QAAgency's `src/memory/*` (MIT; credited in
`THIRD_PARTY_LICENSES.md`). This is a much smaller, privacy-first version.

## What you see

* **Overview card "What we remember about this site"** (project **Overview** tab, once an analysis has finished).
  * After the first analysis it explains that there is nothing to compare with yet and that notes were saved.
  * After later analyses it shows one line, for example **"Since the last analysis: 2 new pages, 1 page changed, 1 page no longer
    found, 1 endpoint gone."**, with **See what changed** listing the page paths and endpoints behind each number.
  * Underneath: how many pages, journeys (and how many have a passing test) and API endpoints are remembered, and when the site was
    last analysed.
  * **Forget what we learned** asks for confirmation ("Forget what we learned about this site? The next analysis starts from scratch."),
    then clears the notes. **Keep it** changes nothing.
  * Empty, loading and error states: "Nothing has been learned about this application yet", a skeleton while loading, and
    "Could not load what we remember" with **Try again** (this never affects your tests).
* **"Start from what we learned last time"** checkbox under **Advanced options** when starting an analysis (on by default; web target).
  Switching it off makes that one analysis neither read nor update the notes.
* **Job events** in the technical details: `memory_used` ("Using what was learned on 2026-10-01: ..."), `memory_changes` (the change
  line), `memory_saved` (first analysis), and `memory_warning` (a plain-language warning, see below).

## The change summary

Computed by the platform from the notes of the previous analysis and the new one:

| Line | Meaning |
|---|---|
| new page(s) | a page address that was not in the notes |
| page(s) changed | same address, but its **fingerprint** differs (its headings or form field names changed) |
| page(s) no longer found | in the notes, but not reached by this crawl |
| new endpoint(s) / endpoint(s) gone | an API method + path template appeared / was not seen this time |
| journey(s) no longer validating | a journey that had a validated test last time has none now (or is no longer identified) |

* A page that is not found is reported as **"no longer found"**, never as "deleted": the crawl may have been smaller (page limit), or the
  page may sit behind a login that failed this time. Likewise "endpoint gone" means "not seen".
* The page fingerprint is a hash of the page's headings (numbers blurred, so a cart counter or a date does not look like a change) and of
  each form's purpose and field names. Page text, links and layout do not count.
* Journey checks only happen when the analysis really planned scenarios; if planning failed, the last known validation is carried over
  instead of reporting a false regression.
* After the first analysis (or after forgetting) there is no change line, only the explanation.

## What is stored — structure only

Per project and application address (origin), one record of at most **64 KB**, versioned:

* purpose and site type (one short sentence each);
* **pages**: path (no query string, ids/e-mail addresses/tokens in paths replaced by `{id}` / `{email}` / `{token}`), page type, a title
  cut to 80 characters, and the 16-character fingerprint; for exploration reuse also a second 16-character fingerprint (title, controls'
  roles and names, API calls; a hash only) and the AI's one-sentence purpose of the page (scrubbed, at most 200 characters);
* **journeys**: name, priority, whether sign-in is needed, the page paths, and the titles of the planned scenarios that **validated**;
* the sign-in path, and **API endpoints** as method + path template;
* a one-paragraph summary generated by the platform ("ecommerce site, 5 pages, 2 journeys (1 with validated tests), 2 API endpoints,
  sign-in at /login.").

**Never stored:** credentials, tokens, page text, accessibility snapshots, link text, form labels, placeholders or values, journey
steps, request/response bodies, example URLs with query strings. As a second line of defence every free-text field is scrubbed:
the project's own credential values (usernames, passwords, tokens, API headers, OAuth secrets, test-account details) are removed
wherever they appear, and e-mail addresses, bearer/JWT tokens and long random-looking strings are replaced. The tests store a crawl of a
site full of recognisable text and a real login, then search the stored JSON for every such value.

The title, the page purposes and the model-written names are the only free text, and they are short and scrubbed. They are given to the model on the next
run, as page text already is; the memory section tells the model the crawl is the source of truth.

## How the notes are used (and not used)

1. The crawl runs **in full**, exactly as without memory. Memory never filters, limits or reorders discovery.
2. After the crawl the platform compares it with the notes (pages and endpoints) and adds a bounded **"Previously known about this
   application"** section (about 5,000 characters at most) to the **understanding** and **planning** prompts: type and purpose, known pages,
   journeys (with the tests that validated), endpoints, and what the new crawl shows compared with that. The section ends with rules: use
   it to keep names stable and focus on what is new; do not describe or plan anything the crawl data does not show; a page missing from
   the crawl is reported as missing.
3. **Exploration reuse** (on by default, see [repair-and-reuse-without-ai.md](repair-and-reuse-without-ai.md)): a crawled page whose two
   fingerprints match the notes is given to the understanding step as one line with its remembered purpose instead of its snapshot. The
   crawl is unchanged; "Send every page to the AI again" (`fullExploration`) or the switch in Settings turns it off.
4. After validation the platform distils the new notes, compares them with the old and stores both (the notes and the change summary).
   Notes are only saved when the understanding step succeeded and the job ran to the end (a cancelled or crashed job leaves the old notes).

## Controls and API

* **Job option `useMemory`** (default `true`): `false` = the analysis neither reads nor writes the notes. Stored on the job like the other
  options; a non-boolean is a `400`.
* `GET /api/projects/:id/memory` → `{ remembered: false, message }` or `{ remembered: true, updatedAt, analysedAt, origin, siteType,
  purpose, learned, loginPath, counts: { pages, journeys, endpoints, journeysWithValidatedTests }, pages: [{ path, type, title }],
  journeys: [{ name, priority, validatedTests }], changes: null | { since, pagesAdded[], pagesRemoved[], pagesChanged[], endpointsAdded[],
  endpointsRemoved[], journeysNoLongerValidating[], text } }`. Fingerprints and the raw record are not returned. Lists are capped at 50;
  `text` is built from the true counts.
* `DELETE /api/projects/:id/memory` → `{ forgotten: true|false }`. Idempotent. Unknown projects are `404`.

## Safety and limits

* **Per project.** Every read and write is scoped by project id; one project's notes never reach another's prompts or answers. Notes are
  deleted with their project. A project keeps notes for up to 5 application addresses (the oldest are dropped).
* **Survives restarts** (SQLite, migration slot 10, table `site_memory`).
* **Versioned.** A record saved by a different version of the platform is ignored (and left in place), with a warning event; the analysis
  carries on and saves fresh notes.
* **Damaged or oversized records** are deleted with a warning event ("...was damaged or too large, so it was discarded"); the job is
  never failed by memory. Any error while saving is a warning event too.
* **Web analyses only.** API-only jobs, re-validation jobs and browser-compatibility jobs neither read nor change the notes. The CLI has
  no memory (it has no store).
* Pages beyond the crawl's page limit that were seen last time show up as "no longer found" when the limit is lower now; raise the limit or
  read the line with that in mind.
* The change summary is only as good as the crawl: a login that fails this time hides the pages behind it.
* Journey-to-scenario matching uses the link the planner wrote (`journey`), or else the scenario's start page being one of the journey's
  pages. A scenario without either does not count towards a journey.

## For developers

* Engine: `src/engine/memory/` — `types.ts` (zod schemas, limits), `distill.ts` (AppModel → record, scrubbing, fingerprints, size cap),
  `diff.ts` (change summary), `context.ts` (bounded prompt section), `session.ts` (one run's use of memory; the orchestrator calls
  `openMemory`, `noteCrawl`, `context`, `analysed`, `remember`).
* Platform: `src/platform/memory-store.ts` (migration, save/load/forget), `src/platform/routes/memory.ts`; `RepoSink` implements the
  optional `loadMemory` / `saveMemory` of `GenerationSink`. `RunnerDeps.makeLlm` lets tests hand the worker a scripted model double.
* UI: `web/src/features/memory/` (`SiteMemoryCard.tsx`), hooked into `ProjectOverview.tsx` and `NewProject.tsx`.
* Tests: `tests/memory.test.ts` (distillation, fingerprints, change-summary table, size, versions, corruption, isolation, API, session),
  `tests/memory-pipeline.test.ts` (real jobs through the worker on a site that changes between two analyses, with a scripted model
  double; fixture `tests/fixtures/memory-site.ts`), `tests/memory-ui.test.ts` (the Overview card journey and the checkbox).
