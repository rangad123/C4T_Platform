# Add a runner as a guided download

What changed for the tester: **Add a runner** is three plain steps and a download, not a token and a command. Nothing to copy, nothing to type in a terminal except, on a Mac or Linux, one short line.

## What the tester gets

Runners, with the project chosen (`#/runners?project=<id>`). The section says "Runners are the computers that run this project's tests. Nothing runs until one of them is online." Connected runners come first; **Add a runner** opens a panel with a "Step N of 3" line. Add a runner, the Access for runners card, Remove access and the Advanced token panel are shown only when the server's `GET /api/projects/:id/runner-access` answers `canManage: true` (the token list is not polled otherwise); everyone else gets a line pointing to **Add this computer** (`runner-personal.md`).

1. **Choose the computer.** Windows or Mac or Linux (preselected from the browser's platform), a name (default "Office computer", 1 to 60 characters), a one-sentence "what is a runner", and the note about phones and visible browser windows. A calm warning appears when the platform says its address will not work from another computer (`urlOk` false); a plain remark when the address works but carries a note (`urlWarning` with `urlOk` true). When the server has no runner download (`available` false) the panel shows the server's reason, tells the person to ask whoever runs the platform, links the guide, and disables **Continue**.
2. **Download and unzip.** A notice about the secret comes before the button. **Download runner** posts to the platform and saves the zip as an ordinary browser download under the file name the server gives. The page keeps only the file name and the id of the new access (header `x-runner-token-id`); it never reads inside the zip and never shows a token. Errors are calm callouts with **Try again**: 409 (limit reached, points to Access for runners), 503 (not built here), 400, 429 and others show the server's own sentence. **Download again** makes new access and says so.
3. **Start it.** Instructions for the chosen computer, the Node.js note (on a Mac or Linux: open Terminal, type `cd` and a space, drag the unzipped folder into the window, press Enter, run `sh start-runner.sh`; the right-click, Open route for `start-runner.command` is given as the alternative; on both systems one line says "If it says it cannot find Node.js but you have it, open Terminal and run node --version there. If that works, run start-runner.sh from that same window."; the slow-connection reasons say the same instead of "Node.js is not installed"), and a status line that polls the runner list every 3 seconds while the panel is open and the tab is visible. It matches the runner by the access made for the download, then by the typed name, then by any runner that was not online at download time and is now. "Connected: NAME is online" shows **Done**. After 3 minutes it adds "Still waiting. Common reasons:" (window closed, Node.js missing, firewall, https), the address problem first when the address looked wrong. It still notices a late connection.

**Installer or plain files (added with the runner installer).** When the server reports installers (`installer` in the info answer), step 1 also asks "How do you want to set it up?": **Installer (recommended)** or **Plain files (advanced)**. The installer is preselected for Windows, and for a Mac; a Linux browser gets plain files (the app is for macOS). An installer the server does not have for the chosen computer is disabled with "This server has not prepared an installer for this computer yet. Ask whoever runs the platform, or use plain files." A server that does not report installers shows no choice and the page asks for plain files. The page always sends `kind` explicitly. Step 3 for the installer says: open the folder, double-click **AITestingRunnerSetup.exe** (Mac: "AI Testing Runner"), that Windows may say "Windows protected your PC" (More info, then Run anyway) or macOS "unidentified developer" (right-click, Open) because it is not signed yet, that it checks what the computer already has and only downloads what is missing, and that Node.js need not be installed first. If the server answers with plain files after the installer was asked for (`x-runner-kit-kind: files`), step 2 says "You got plain files, not the installer" and step 3 shows the script's steps. The slow-connection list names the setup window instead of Node.js.

**Complete download (added in round 17, `runner-complete-kit.md`).** When the info answer's `complete.targets` has at least one built target, the choice has three ways in this order: **Complete download (recommended)** with its size ("about 56 MB"), **Installer** (no longer marked recommended there), **Plain files (advanced)**. The complete download is preselected when it exists for the guessed computer; when none was built for the chosen system it is shown disabled with "This server has not prepared the complete download for this computer yet. Ask whoever runs the platform, or choose another way." and the installer is recommended as before. A **System and processor** list (only the targets of the chosen system; ones not built are listed as "(not prepared on this server)" and cannot be chosen) is preselected from `navigator.userAgentData.getHighEntropyValues(["architecture", "bitness"])` where the browser has it, otherwise from the user agent (a Mac counts as an Apple chip, because a Mac's browser always says Intel), and says "We guessed Windows on an Intel or AMD processor. Change it if that is wrong." The page sends `{ name, platform, complete: true, arch, os? }`. Step 2 says "We make a complete download for NAME on Windows on an Intel or AMD processor, about 56 MB. It holds its own Node.js and test tools, so nothing else is installed." Step 3 gives the start script's steps with "It starts straight away: this download already has Node.js and the test tools, so nothing is installed.", mentions `AITestingRunnerSetup.exe` as the alternative when the server has the Windows installer, says Node.js is not needed, and the slow-connection list names "the download is for another processor" instead of a missing Node.js. A server without complete builds shows the panel exactly as before.

The installer's step 3 now says it only downloads Node.js and the test tools: neither the installers nor the start scripts download a browser any more (the runner does, when it must).

**Runners list.** Each card shows name, online or offline, what it can run, the version and the **runner download version** when the runner reports one, and **Remove access** (revokes the access behind it, after "This runner will stop and can't connect again. Tests keep their results."). A new **Access for runners** card lists every active access, including downloads nobody started yet, each with **Remove access**. Empty state: "No runners yet" and an **Add a runner** button.

**Advanced: start a runner from the project folder** (closed by default) keeps the earlier way: create a token, run the command, unchanged.

## How it works

- API (KIT-A, `src/platform/routes/runner-kits.ts`): `GET /api/projects/:id/runner-kits/info`, `POST /api/projects/:id/runner-kits` (zip, header `x-runner-token-id`). The web code is `web/src/features/agents/` (`AddRunner.tsx`, `kit.ts`, `RemoveAccess.tsx`, `AgentsList.tsx`, `ProjectRunners.tsx`, `add-runner.css`).
- The platform sends the kit version inside the runner's `capabilities.kitVersion`; the card reads it from there.
- Focus moves to each step's heading; Escape closes the panel (a confirmation dialog closes first). Polling stops when the panel closes.
- Test-only knob: `?runnerWaitMs=1500` in the page address shortens the 3 minute wait (accepted from 500 ms to 3 minutes; anything else is ignored).

## Limits

- The page cannot tell that the runner started; it sees it only once the runner connects to the platform. A runner that connects under a name and access it was not given by this download is not recognised as new unless it was offline before.
- The download makes new access every time; unused access stays until removed.
- A runner started from a kit is checked by tests with a stand-in bundle (the routes, zip and access are real; the program inside is a placeholder) unless `npm run build:runner` has been run on the machine.
