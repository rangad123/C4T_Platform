# Reusable steps (blocks)

Save a group of steps once, such as signing in, and use it in many tests. When the steps change, every test that uses them follows.

## What a person sees

- **Tests page, More actions, Reusable steps** (`#/projects/:id/blocks`): the project's reusable steps with their kind, values, step count and the tests that use them. Add, change and delete them there. The editor is the same one the test builder uses (forms, add-a-step list, shared elements). Inside a block, the value inserter offers the block's own values.
- **Edit steps (the builder)**:
  - *Add a step* has a group "Reusable steps". A set with values opens a small form for them; a blank value uses the default.
  - A use is a collapsed row, "Run the reusable steps “Sign in”". Open it to choose other steps, set values, read the steps inside, or follow "Edit the reusable steps".
  - *Save steps as reusable steps* turns a range of consecutive steps into a block and puts a use in their place. A "value" can stand for text inside the steps (for example `Linus`); the use gives the same text back, so the test's script does not change and it needs no new run.
- **Test page**: a use shows as one step with "Show the steps inside", and takes its result from the steps that ran.
- **Objects page**: a shared element that is only used inside reusable steps still shows its tests. The line under the element reads "Used by 2 tests: Ada signs in (through the reusable steps “Sign in”), ...", and an element a set holds that no test uses yet reads "Not used by a test yet. Held in the reusable steps “Count it”" and cannot be deleted.

## How it works

A block is `{ name, description?, kind: web | api | any, params: [{ name, description?, default? }] (max 10), steps (max 40) }`. A test uses it with a step `{ "action": "useBlock", "block": "Sign in", "args": { "email": "a@b.test" } }`. The stored spec keeps this one small step.

Before any script is rendered or run, the step is replaced by the block's steps (`src/engine/blocks/expand.ts`):

- `{{name}}` in the block's text fields is replaced by the value given, else the default. A missing value without a default is a plain error naming the parameter. The value is data: it is never evaluated and not looked at again, and generators escape it like any other text. Words that say what a step does (action, check, method, how an element is found, a shared element's name) are never replaced.
- Blocks may use blocks, up to 3 levels. A circle is refused and named. A test never grows past 100 steps once blocks are in place, **and never holds more than 400 KB of step text** (the sizes of the steps as JSON, counted while they are built). Every other limit is per block or per value; nested blocks multiply them (a 500 character value passed down three levels, into a step that uses it 2 500 times, would be a gigabyte), so the budget is spent as the steps are made and the work stops the moment it is used up: nothing larger than the budget is ever built, and the test fails with a plain sentence ("... would hold more than 400 KB of step text ...") instead of a server error. The same budget protects every reader (the test list and page, reports, the scheduler, the job runner), so one stored set that is too large costs one failed test, not the server.
- Generators never see a `useBlock` step: the expansion happens in `renderWithAdapter` / `renderScript`, and the generators refuse one if it reaches them. The job runner expands (then resolves shared elements) before the engine sees a spec, so health checks, load/production decisions and run results all work on the steps that really run. A test with no block is returned as the same object, so its script and answers are byte-identical to before.
- The engine may store a spec again after a run. Every expanded step carries a note of where it came from, and `repo.updateTest` folds an unchanged group back into the one `useBlock` step. A group changed on the way (an AI repair) stays as plain steps.

## Rules

- **Shared checks.** A block is judged the way a test using it would be: the same address guard, the "stored sign-in details only on the application's own site" rule, secret checks and renderer, run on the expanded steps (`SpecEditService.evaluate` with the proposed blocks). The same applies when a test is saved, imported or edited, and when a block changes.
- **Changing a block.** Checked against every test that uses it, directly or through another block, and against other blocks that reach it. If one would break, nothing is saved and the answer lists the tests with the first reason. Checking awaits (addresses are looked up), so what the checks relied on (every set and its version, and the steps of every test that uses this one) is read again inside the transaction that stores the change; if it differs, the answer is a 409 "Something that these reusable steps depend on was changed while they were being checked ... Nothing was saved" and the person reloads and tries again. "Save as reusable steps" does the same with the test it takes steps from and the sets of the project, so a save of the same test in that window is never overwritten. Otherwise those tests are rendered again and one validation job is queued (or the tests are marked as waiting with the reason, like a shared-element change). Hand-written tests are skipped. A rename follows in every spec and block that uses the name.
- **Deleting** is refused (409) while a test or a block uses it, listing them.
- **Caps**: 100 blocks per project, 40 steps and 20 KB per block, 10 values, depth 3, 500 characters per value, 100 steps and 400 KB of text for one test once the steps are in place.
- **Refused before they are stored** (blocks API create and change, "save as reusable steps", a spec import, a backup restore): a set that would put more than 100 steps in place (worked out from the graph of sets, nothing is built; the count stops one above the cap, so a graph of billions of steps costs the same as one of 101), and a set that grows past the text budget when it is given the longest allowed value (500 characters) in every parameter. The second check is a real expansion with that value, stopped at the budget, so it can't pass a set that a long value would later break; its price is that a set that needs more than 400 KB with 500 character values in every parameter is refused even if every test would give short ones. A hostile `blocks.json` or import is refused with a plain 400 naming the first set, and nothing is created.
- **Isolation**: a test can only use blocks of its own project; every lookup is by project.
- **Audit**: create, change, rename, delete and extraction are recorded in the project's audit trail (`custom_audit`), which keeps the newest 1 000 rows per project like the rest of that trail. The platform has no notion of who is acting (one API key; the routes pass no name), so the rows say what happened, not who did it; the `by` parameter of the service is ready for the day an actor exists.
- **The test page** puts only its own reusable steps in place. Its quality note ("it has exactly the same steps as ...") needs the earlier tests only to compare steps, and two tests can be copies only if they have the same number of steps once the steps are in place, so another test that uses reusable steps is expanded only when its step count (from the graph) matches. The list of a project's tests still puts in place the steps of every test that uses a block (and no other test); with the budget above that is bounded work per test. Projects without reusable steps get the answers they always got.
- **No application yet.** A set can be saved before the project has an application. The checks that need no address (schema, caps, circles, depth, size, typed secrets) always run, and so do the others against a stand-in address (`https://application.invalid`, never contacted): the address guard refuses a step that reaches a private or metadata address, the sign-in rule refuses stored sign-in details on any other site, and the script is rendered. The answer carries `notes` saying so; it is absent when the project has an application, so those answers are unchanged. Because a set saved with a stand-in address has not met the real one, the next save of any set after the project's first application also looks at up to 20 sets last saved before that application and adds a note for each that fails (it informs, it never stops a save). A test that uses a set is always judged on the expanded steps against the real address when it is saved, so a first use is checked in full.
- Production-safety decisions (does this test change data, is it a load check, deletable records for cleanup) and reports (quality, compliance, scheduled run selection) look at the expanded steps.
- Shared elements used inside blocks: an element in use by a block cannot be deleted, a rename rewrites the block, and a locator change reaches the tests that use the block.

## API (behind the API key)

- `GET /api/projects/:id/blocks` (list, `?q=`, `?kind=`; also the editor's catalog and placeholders), `POST` (create).
- `GET|PUT|DELETE /api/projects/:id/blocks/:name` (name ignoring case; `PUT` takes any of name, description, kind, params, steps, `expectedVersion`).
- `GET /api/projects/:id/blocks/:name/usage`.
- `POST /api/projects/:id/blocks/from-steps` with `{ testId, from, to, name, description?, params?: [{ name, default?, replace? }] }` (0-based, inclusive). It refuses hand-written tests, a range that breaks a rule, a name that is taken, and any extraction that would change the steps that run. It records the test's earlier steps in its step history.
- `GET /api/tests/:id` adds `runSteps` for a test that uses blocks.
- **Export and import.** `GET /api/projects/:id/specs` adds `blocks` (name, description, kind, params, steps; no ids) with the sets the exported tests use, directly or through other sets, and `objects` also lists the shared elements those sets refer to. The project zip (`GET /api/projects/:id/download`) adds `blocks.json` (`{ version: 1, blocks: [...] }`) the same way, for the specs it contains. A project whose exported tests use no block gets exactly the answer and the zip it always had. `POST /api/projects/:id/specs` accepts `blocks` (at most 100) and checks them as a whole before anything is stored, with the rules of the blocks API: size and name rules, a typed secret, a circle or too deep a chain, the address guard and the sign-in rule when a set is used on its own, and the shared elements it refers to (those already in the project or brought by the same import). A name the project already has must be the same steps (kind, values, steps): then it is reused; a different set with that name is refused with 409 and a plain sentence, and nothing is stored. The tests in the import are then judged on the steps that run, as always, so a set that sends stored sign-in details elsewhere is refused through the test too.
- Migration slot 25 (`step_blocks`). Backups carry `blocks.json` (absent when there are none); a restore runs the same checks again and refuses circles, too-deep or oversize blocks, sets that grow past the step or text budget, typed secrets, and tests whose blocks are missing (400, nothing created).

## What is not covered

- AI generation, planning and repair never create or use blocks. A repair of a test that uses blocks is kept as plain steps; locator-healing suggestions are not offered for such tests.
- Blocks are for web and API tests in the builder. A mobile or desktop spec can use a block of kind "any" by import only.
- Hand-written (custom) tests do not use blocks.
- A spec import brings sets only from the `blocks` list of the same request. It never copies sets from another project by name, and a set that no imported test uses is still stored when it is in the list. The import does not carry a set's audit trail or version.
- A spec import without an application address checks an imported set the same way a saved one is (stand-in address, see above).
- The save-time size check is made on the sets with the longest allowed value in every parameter. A test that gives values of its own is judged by expanding it with them (when it is saved in the builder or imported, and every time it is read or run), under the same budget.
- A set whose name is longer than the step allows: both are limited to 80 characters (the step's limit and the name rules agree).
- The "used by" count and the tests listed for a shared element are read from the specs and the sets when you ask (not from a stored table), so they cannot drift. A test is counted once, however many of its steps reach the element.
- A failing step of a test with blocks is shown on the step that uses the block. Sentry's step lookup and the steps listed in an issue created from the test use the steps that ran (the numbers a run reports). The severity score itself never used step numbers.
- Values are plain text replacement: there are no conditions, loops or computed values.
